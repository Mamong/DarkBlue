# 蓝牙协议设计


在蓝牙协议设计中，如果你需要传输大数据（长数据），不应该依赖“连续读取（Read with Offset）”，因为它的效率极低。
以下是针对大数据传输的专业协议设计思路：
## 1. 放弃“Read”，改用“Notify + 流控”
Read 操作由中心设备发起请求，外设回复，一问一答（Round-trip Delay），速度慢。
推荐方案：

* Notify（订阅）：外设主动推送，不需要等待确认（如果是 Indicate 则需要确认，速度稍慢）。
* 流控机制：
1. 中心设备写入一个“开始传输”指令。
   2. 外设开始连续发送 Notification 数据包。
   3. 每发送 $N$ 个包，中心设备回复一个“已收到”或“继续”，防止缓存溢出。

## 2. 获取并利用最大 MTU
不要写死切片大小。在发送前，动态获取当前连接支持的最大包长度。

* 代码参考：central.maximumUpdateValueLength。
* 切片大小：通常设置为 MTU - 3 字节（ATT 头占用 3 字节）。

## 3. 数据封包协议设计 (Packet Structure)
既然系统不会自动帮你重组，你就需要在应用层定义一套精简的协议头。
推荐的数据包格式：

| 字节偏移 | 字段名 | 长度 | 说明 |
|---|---|---|---|
| 0 | Type | 1 byte | 0x01: 开始, 0x02: 数据, 0x03: 结束 |
| 1-2 | Seq No | 2 bytes | 序列号（用于检查丢包/重组顺序） |
| 3-4 | Length | 2 bytes | 本次有效载荷长度 |
| 5-N | Payload | 剩余 | 实际数据内容 |
| 最后 | CRC/Checksum | 1-2 bytes | (可选) 校验整段数据的完整性 |

## 4. 传输逻辑流程

   1. 握手阶段：中心设备写入一个控制特征值，告诉外设：“我要读那个 50KB 的文件”。
   2. 外设切片：外设根据 maximumUpdateValueLength 将数据切成 $X$ 个块。
   3. 循环发送：外设使用 updateValue(_:for:onSubscribedCentrals:) 快速发送。
   * 注意：如果该方法返回 false，说明发送队列满了。你需要实现 peripheralManagerIsReady(toUpdateSubscribers:) 代理方法，等队列清空后再继续发送剩下的包。
   4. 完成校验：所有包发完后，发送一个 Type = 0x03 的结束包，附带整段数据的 CRC 校验码。

## 5. 为什么不建议用 Read？

* 用户体验差：Read 过程中 UI 往往会阻塞或者无法实时显示进度。
* 功耗高：射频开启时间更长。
* 可靠性低：一旦其中一个 Offset 请求失败，整个重组逻辑在应用层很难优雅恢复。

你是准备传输文件、图片，还是长文本数据？ 不同的场景对校验（Checksum）和流控的需求强度不同。
